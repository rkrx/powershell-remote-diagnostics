# Encrypted gRPC and MCP Client Implementation Plan

> **For agentic workers:** Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox syntax for tracking.

**Goal:** Replace REST with an encrypted gRPC Windows server and a self-contained local MCP client with optional Avalonia connection entry.

**Architecture:** Retain the server execution/output core. Share generated protobuf contracts and connection-token validation in a PowerShell-free transport library. A local MCP client owns pinned TLS channels; its optional Avalonia entry subprocess communicates through an inherited private pipe.

**Tech Stack:** .NET 10, official Microsoft.PowerShell.SDK 7.6.8, gRPC .NET 2.85.0, Google.Protobuf 3.36.2, official MCP C# SDK 2.3.0, Avalonia 12.1.4, xUnit.

**Spec:** `docs/superpowers/specs/2026-10-31-grpc-mcp.md`

## Global constraints

- Preserve Windows 10 Pro 22H2 and Server 2016 as compatibility targets; actual OS acceptance is separate from Windows Server 2022 CI.
- Preserve all execution/approval/pagination semantics; REST is removed, not maintained in parallel.
- No insecure certificate bypass, secret logging, execution retries, or credentials in GUI process arguments/files.
- English generic public source/docs; private local notes stay outside Git.
- The user explicitly authorized planning followed by immediate implementation; no second approval gate.

## Review focus

- Incorrect certificate/expired certificate, wrong token or malformed URL must fail before execution, without leaking credentials.
- Explicit working connection URLs must not launch GUI; missing data must prompt; cancellation and unavailable desktop must fail clearly.
- Client disconnect/timeouts must not rerun or silently cancel accepted scripts.
- Unknown/evicted UUIDs, pending output and invalid paging/search ranges must retain distinct gRPC errors.
- Packaged Windows/macOS clients must start MCP cleanly without PowerShell and packages must contain actual runnable dependencies.
